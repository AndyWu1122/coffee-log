# 咖啡社群：開工前待決事項

搭配 [social-spec.md](social-spec.md)。規格原文不修改，這裡列出規格沒寫清楚、開始階段 1 之前要先決定的事。
每一項決定後填在「決定」欄，再據此寫階段 1 的完整計畫。

前提：Supabase 的 anon key 會公開在前端，**任何人都能繞過 App 直接呼叫 API**。
所以只寫在前端的限制，對攻擊者等於不存在；所有規則都要在資料庫（RLS、check、trigger、函式）強制。

---

## 1. 用好友代碼找人，可能變成「搜尋所有使用者」

- **問題**：如果 profiles 表允許用代碼查詢，攻擊者可以大量猜代碼，把使用者列出來。
- **建議**：
  - profiles 只給「好友」和「有待處理邀請的對方」讀
  - 加好友改用資料庫函式 `send_friend_request(code)`：輸入代碼、直接送出邀請、**不回傳對方資料**；代碼不存在和已送過都回傳一樣的訊息
  - 代碼至少 10 碼隨機英數，避開易混淆字元（0/O、1/l），可以重新產生
  - 限制輸入代碼的次數（例如每小時 10 次），失敗也算
- **決定**：採用建議（2026-10-24，階段 1 已實作）。profiles 只給本人、有好友關係或待處理邀請的對方讀；`send_friend_request(code)` 不回傳對方資料；代碼 10 碼、31 個字（不含 0 O 1 I L），可用 `regenerate_friend_code()` 重新產生；每小時打錯 10 次就暫停（只算「找不到」，正常邀請受每日上限限制）

## 2. 每日上限必須在資料庫強制

- **問題**：「每天最多 20 個好友邀請、30 筆紀錄」只在前端擋的話，直接打 API 就能無限送。
- **建議**：用 trigger 或 RLS 的計數條件強制；測試加上「第 21 個邀請、第 31 筆紀錄會失敗」
- **待決**：「每天」用哪個時區算？「修改」既有紀錄算不算在 30 筆裡？
- **決定**：台灣時間的日曆日；只算新增，修改不算；次數記在 `private.rate_events`，刪掉再新增不會還回來（2026-10-24，階段 1 已實作）

## 3. Google 登入一定會存 email

- **問題**：規格寫「只收暱稱和頭像」，但 Supabase Auth 會在 `auth.users` 存 Google 帳號的 email（避不掉）。
- **建議**：
  - 隱私說明頁誠實寫出「會存 email，只用於登入，其他使用者看不到」
  - 確認沒有任何 view、函式把 `auth.users` 的 email 露給其他使用者
  - 頭像不要直接用 Google 大頭貼，只用使用者自己上傳的（同樣壓縮、去 EXIF）
- **待決**：台灣個資法要求告知蒐集目的與使用方式；隱私說明頁要不要另外請人看過？
- **決定**：

## 4. 檢舉送出去之後由誰處理

- **問題**：規格有 reports 表，但沒有管理者或審查流程，檢舉會石沉大海。
- **選項**：
  - A. 不做檢舉，只做封鎖（內容只有好友看得到，封鎖已足夠）
  - B. 做檢舉，由我（站長）定期在 Supabase 後台查看並處理
- **建議**：A。只對好友可見的社群，封鎖比檢舉有用；之後真的需要再加
- 如果選 B：reports 只能新增、不能讀（連檢舉者自己都讀不到別人的檢舉），也要限制次數
- **決定**：照規格保留 reports：只能新增、任何人都讀不到，由站長在 Supabase 後台查看；每人每天最多 10 次；只能檢舉看得到的別人紀錄（2026-10-24，階段 1 已實作）

## 5. likes 的權限

- **問題**：規格沒寫 likes 的 RLS。如果誰都能對任意 id 按讚或讀讚數，可能被拿來推測某筆紀錄是否存在。
- **建議**：只有讀得到那筆紀錄的人才能按讚、看讚；只能新增、刪除自己的讚；同一人對同一筆只能一個讚（unique 約束）
- **待決**：讚數要不要顯示是誰按的？（好友之間應該沒關係）
- **決定**：採用建議；讚數會顯示誰按的（好友之間），讀取權限跟著紀錄走（2026-10-24，階段 1 已實作）

## 6. 刪除帳號需要伺服器端程式

- **問題**：刪除 Supabase 的使用者帳號需要 service_role 權限，不能在前端做。
- **建議**：用 Supabase Edge Function 實作「刪除我的帳號」
  - 金鑰只存在 Supabase 後台的環境變數，不進 repo
  - 函式先確認呼叫者身分（JWT），只能刪自己
  - 依序刪除：Storage 照片 → 資料表（用外鍵 `on delete cascade`）→ auth 使用者
- **待決**：刪除要不要有緩衝期（例如 7 天內可取消），還是立即刪除？
- **決定**：所有資料表的外鍵都是 `on delete cascade`（刪除 auth 使用者就連帶刪除）；Edge Function 與緩衝期在階段 5 決定

## 7. 封鎖的連帶效果

- **問題**：規格只寫「有封鎖關係時雙方都讀不到」，沒寫封鎖時既有的關係怎麼處理。
- **建議**：封鎖時同一個交易裡
  - 解除好友、刪除雙方之間的待處理邀請
  - 被封鎖者不能再送邀請（`send_friend_request` 檢查 blocks，回傳和「代碼不存在」一樣的訊息，不透露被封鎖）
  - 被封鎖者讀不到封鎖者的 profile、紀錄、照片、讚
  - 封鎖者可以解除封鎖，但不會自動恢復好友
- **決定**：採用建議（2026-10-24，階段 1 已實作）。另外：A 封鎖 B 後，A 若用 B 的代碼送邀請會得到 `you_blocked`（提醒先解除封鎖）

## 8. 測試環境

- **問題**：RLS 測試需要建立多個帳號、用最高權限準備資料，不能碰正式資料。
- **選項**：
  - A. 本機 Supabase（Supabase CLI + Docker），完全離線、可重設
  - B. 另開一個 Supabase 測試專案
- **建議**：A。正式專案只用來跑正式資料；service_role key 只放在本機 `.env`（階段 1 已把 `.env` 加進 .gitignore）
- **待決**：這台電腦能不能裝 Docker Desktop？
- **決定**：A：本機 Supabase（`npx supabase@2.120.0 start`，Docker Desktop 已可用）

## 11. 階段 2（照片）的決定與已知限制（2026-10-24）

- **照片權限跟著紀錄走**：只有 shared_brews 裡自己的紀錄 `photo_path` 指向該路徑時才能上傳；讀取要讀得到那筆紀錄。
  好處：照片數量受每天 30 筆紀錄限制（bucket 不會被當硬碟塞滿）；紀錄刪除或移除照片時，就算檔案還沒刪，好友也立刻讀不到
- **只接受 JPEG／PNG／WebP**（規格原文）：本機沖煮紀錄的照片也一起改，`accept` 只列這三種；iPhone 的 HEIC 通常由系統在選取時轉成 JPEG，轉不了會提示改成「最相容」
- **上傳前再清一次中繼資料**：Chrome 的 canvas 輸出會帶通用的 sRGB 色彩設定檔（APP2 ICC_PROFILE，不含個人資訊），本機照樣保留；上傳前 `photoForUpload` 移除 JFIF 以外的所有段落
- **已知限制**（Storage 本身做不到，不另外處理）：
  - Storage 只看上傳時的 Content-Type，不檢查內容、也不能移除 EXIF。繞過 App 上傳的人只能放進自己的資料夾，洩漏的只會是他自己的資訊
  - signed URL 的效期由前端決定，好友直接打 API 可以要更長的效期；而且網址發出後不再檢查 RLS，解除好友或封鎖前拿到的網址到期前仍可用。
    好友本來就看得到、也能存下這張圖，所以不算權限擴大
  - SQL 不能直接刪 `storage.objects`，照片要用 Storage API 刪除（階段 4 同步、階段 5 刪除帳號時處理）

## 12. 階段 3（帳號與好友）的決定（2026-10-24）

- **正式專案的建立時機**：A，階段 3 本機測試通過後就建，實際用 Google 登入一次（步驟見 [supabase-setup.md](supabase-setup.md)）。套用後 migration 不能再改
- **QR code**：A，內容是網址，用手機內建相機掃，App 不做掃描。iPhone 主畫面 App 和 Safari 登入狀態分開，掃了在 Safari 開時顯示代碼和「複製」
- **頭像**：只用使用者自己上傳的（裁成 256×256、移除 EXIF），不用 Google 大頭貼；只有好友和邀請中的對方看得到（第 3 項）
- **封鎖名單的暱稱**：封鎖後互相看不到 profile，所以封鎖當下由資料庫記下對方暱稱，否則名單顯示不出名字、無法解除封鎖
- **登入狀態**：存在 IndexedDB 的 meta，不放 localStorage；meta 不匯出，所以 token 不會出現在備份檔
- **正式專案必須關閉 Email 登入**：本機測試發現，只關「註冊」時，已存在的帳號仍能用 magic link 登入（本機測試就是用 admin API 這樣拿 session）
- **待確認（要實機）**：iPhone 主畫面 App 用 Google 登入後能不能回到 App；LINE 等內建瀏覽器 Google 會拒絕，App 會提示改用 Safari／Chrome
- **未處理（風險低）**：好友和有待處理邀請的對方讀得到你的好友代碼（profiles 整列可讀）。代碼本來就是要給人的，只能拿來送邀請


## 13. 階段 4（動態牆與同步）的決定（2026-10-24）

- **分頁命名**：底部分頁「好友」是動態牆（`#/feed`）；☰ 選單原本的「好友」改名「好友管理」
- **排序**：依沖煮時間（brewed_at）新→舊。補傳的舊紀錄會排在後面，不會跳到最上面
- **動態牆照片**：雲端只有 1600px 的原圖（每張約 200KB），先不做縮圖；要做得改 Storage 路徑規則（新 migration）
- **不需要新 migration**：現有的 shared_brews、likes、照片權限已足夠
- **同步方式**：比對本機應有的內容和上次同步的內容（sync store），不用動作佇列。好處是離線、沒登入、匯入備份、改豆子名稱都會自動補上
- **多台裝置**：只刪這台裝置認得的雲端紀錄，避免平板把手機分享的紀錄刪掉。代價是：在 A 裝置分享、在 B 裝置「取代全部」匯入一份沒有這筆的備份，雲端那筆不會被 B 刪掉（B 不認得它）
- **每天 30 筆的額度**：改回只有我再改回好友會重新 insert，會再用掉額度（資料庫規定刪掉不還）；撞到上限時同一天（台灣時間）不再重送
- **筆記會分享出去**：選「好友」時表單提示「豆子、參數、風味、筆記和照片都會讓好友看到」；分享卡片的「包含筆記」預設關，是因為卡片會傳給任何人
- **讚的名單**：看得到 profile 的人列出暱稱，其他人（按讚的人不是你的好友）只顯示人數
